## 2. 最终设计与兼容性

- `DATABASE_SCHEMA_VERSION = 2`，独立于 App / Engine / Backup / Share 版本。
- `SAVED_EXAMPLE_SCHEMA_VERSION = 1`；Saved Example、Calculator、Draft、MinimalRuleSnapshot 的既有 DTO 格式不改写。
- 六张表名称及业务索引不变。v2 引入迁移校验记录及只读保留标记，写入既有 `migrationBackups`，没有第七张表。
- Application 定义 `DatabaseMigrationPort` / Service；Infrastructure 的 `DexieMigration` 解析版本路径并执行真实 IndexedDB 事务；UI 不负责迁移。
- 新数据库直接创建 v2；已有 v1 先提交安全备份，再进入独占 versionchange 事务。
- 备份包含旧 Saved、Trash、Draft、RuleSnapshots、RulePackageMetadata 及原始偏好字符串。既有 migrationBackups 原位保留，不递归复制备份。
- 备份事务提交后才返回有效 backupId；备份读写失败不进入迁移，不返回虚假的成功备份 ID。
- 升级事务开始时比较当前数据与备份数据，拒绝备份后发生的并发写入；执行受信任、随 App 发布的迁移步骤及 Schema 校验后才 commit。
- 不执行持久化数据中的 JS、表达式或远程脚本。没有按 ruleId 分支。
- 任一步骤抛错时回滚整个升级事务与数据库版本；已单独提交的安全备份仍保留。
- 不能可靠解析的记录原位保留并记录问题，不删除或“修复”原始内容。当前采用保守的数据库级只读保护：暂停持久写入，仍允许浏览可读的保存时结果及 Temporary Mode Calculator。重新检测存储不能绕过迁移只读标记。
- 高版本数据库不降级；缺失路径不猜测转换。不自动换 Rule Version 或重算 Saved Result Snapshot。

## 4. 迁移前后摘要

v1 → v2 单元 fixture 同时包含：

| 数据 | 迁移前 | 成功后 |
| --- | --- | --- |
| Saved | 1 条 | 1 条；整个记录深相等 |
| Trash | 1 条 | 1 条；modifiedAt / trashedAt 不变 |
| Draft | 1 个 current | 原内容、临时状态字段、编辑信息及 lease 不变 |
| MinimalRuleSnapshot | 保存时生成的快照 | 整个数组深相等 |
| Preferences | 原始字符串 | 保存在迁移前备份中，不在迁移步骤中改写 |
| 既有迁移备份 | 1 条 | 原条目保留；另增本次预备份及 commit 记录 |

浏览器 fixture 使用实际 Calculator 保存产生的 Saved / RuleSnapshot，写入原生 IDB 逻辑 v1 后重新启动 App，验证升级、备份、只读详情、原结果及问题记录保留。没有只用模拟库替代浏览器验证。
