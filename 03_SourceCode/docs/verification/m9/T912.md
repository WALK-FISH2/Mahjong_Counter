## 1. 最终保护机制

1. BroadcastChannel 优先发送变更/让出通知；不可用时用 IndexedDB lease 轮询。
2. 唯一 `draft/current` 的 lease 含 owner、token、expiresAt；heartbeat 为 1500ms，lease 为 6000ms。
3. claim/renew/release/write 均通过同一个 Dexie Draft Repository。写入在读写事务内核对 owner、lease token、有效期和 expected writeToken，不只比较 document revision。
4. Web Locks 提供额外的浏览器互斥，并保护 IndexedDB 失效后的临时编辑。Web Locks 缺失但 BroadcastChannel 可用时使用带 term/稳定 owner tie-break、心跳及过期的广播协调；不把广播当作持久写入事务锁。
5. takeover 期间串行化接管入口，禁止轮询再次获取。旧标签让出后暂停自动争抢，转 read-only；Application Action、Replace Guard 和 UI 均限制编辑，不只是按钮变灰。
6. 接管仍需用户明确“继续上次牌面/放弃草稿并新建”。只获取 lease 不替换或改写草稿正文。
7. 旧标签已排队的写入即使迟到，也会因持有旧 lease/token 被拒绝。丢失所有权不被误判为 Storage failure，不能借 Temporary Mode 绕过 Draft 锁。

## 2. 失败原因及修复

此前 Chromium 接管失败属于实现竞态：旧主标签释放 lease 并发送通知后，次标签自动轮询先获取一次，显式 takeover 随后又获取一次；第一次恢复成功后，后到的第二次获取重新设立 pending 恢复状态。

修复包括：

- takeover 使用 transferring 状态，接管完成前不展示可提交的恢复选择；
- 已发出的异步 poll 在读取结束后再次检查 transferring/disposed；
- 让出标签使用 claimAfter，避免立即重新争抢；
- 增加可控延迟 read 的确定性单元测试，确认显式 takeover 仅调用一次 claim；
- 增加可控延迟 write 测试：takeover 先完成，再放行旧 write，数据库内容仍与新 lease 记录完全一致，旧 controller 真正 read-only。

未通过延长 E2E sleep、移除只读断言或绕过 transaction fence 解决问题。协议中的 200ms 活跃标签让出窗口、广播 fallback 的两阶段 100ms 发现/竞争窗口有明确协调用途；E2E 等待可观察状态，不使用任意 sleep。

## 3. 双标签时序和实际结果

使用同一浏览器 Context 中两个 Page，共享真实 IndexedDB；两个浏览器均执行。

| 场景 | 时序与断言 | Chromium | WebKit |
| --- | --- | --- | --- |
| 正常 BroadcastChannel | A 输入并保存 Draft；B 默认禁用录牌；B 接管并继续 Draft；A 禁用录牌；B 新增牌写入；A 再接管能恢复 B 新增牌，B 转只读 | PASS | PASS |
| 无 BroadcastChannel、无 Web Locks | A/B 同库，事务 lease 保证单写；B 接管后 A 在轮询内转只读 | PASS | PASS |
| 无通知的异常关闭 | 测试拦截 pagehide 清理，关闭 B；不调用正常 release；A 等待 lease expiration 后取得原 Draft；B 最后保存的牌仍在 | PASS | PASS |
| IndexedDB 不可用、Web Locks 可用 | 两标签只有一个可录牌；接管后旧标签禁用，旧内存输入仍在；不声称 Draft 保存 | PASS | PASS |
| IndexedDB 不可用、Web Locks 缺失、BroadcastChannel 可用 | 广播 fallback 限制次标签并完成 takeover，旧标签转只读；持久化持续暂停 | PASS | PASS |

Application/Repository 测试另证明：同时 claim 仅一个成功；旧 lease、旧 writeToken 均不能写；同 revision 不绕过并发保护；失效 lease 可恢复；广播同时竞争只有一个胜者、坏消息被忽略、失去心跳可过期恢复。

## 5. 边界与结论

- 浏览器：Playwright 1.62.1；Chromium 151.0.7922.34 / WebKit 26.5；生产构建，`http://127.0.0.1:4173`。
- 异常关闭采用“阻止清理 + 关闭页面”的可重复故障注入，不声称做过系统进程强杀或真实移动系统挂起测试。
